# 按用户规范开发清晰可维护的代码

> **语言 / Language** · **简体中文（当前）** · [English →](SKILL_en.md)

把命名、职责、状态所有权、错误处理和可生成手册的注释放在同一实现中。排版通过不能代替设计与行为验证。For English-language tasks, use [the English instructions](SKILL_en.md).

## 确定目标与规范来源

- 核对目标项目完整路径、Git 根、协作规则、语言、构建方式和本次修改范围，保留其他未提交工作。此技能的位置不是目标项目根目录。
- 先读取目标项目生效的格式配置和真实模块，再按本次要求选择基准。自有项目使用用户提供的 clang-format 配置；随包的 [格式配置](assets/cpp.clang-format) 是可移植快照。使用及来源见 [格式与手册生成](references/format_and_manual.md)。不要仅检查配置文件存在，也不要静默用工具默认样式代替它。
- 用户配置以 WebKit 为基础，使用 4 空格并禁用 Tab；不能把这一排版宣称为 Linux 内核原生排版。借鉴内核与 Zephyr 的清晰接口、显式生命周期、分层和错误路径；不把二者的所有规则混为一套。修改真实上游代码时先指出与用户偏好的差异，依据本次明确要求及目标贡献约定确定应用方式，不擅自覆盖整个上游格式或文档体系。

## 命名与 Clean Code

- 自有文件、目录、命名空间、类型、类、函数、方法、变量、成员及协议字段使用英文 `snake_case`；宏和常量可用 `UPPER_SNAKE_CASE`。类名也不改用 `PascalCase`，普通自有接口不使用 `camelCase`。
- 语言语法、系统或第三方契约强制的名称保持原样，例如覆写方法和外部 ABI；列清边界，不以框架常见风格扩大例外。改名时同步真实调用方、构建入口、序列化字段和文档，不用机械替换破坏外部契约。
- 一个函数完成一个可命名的动作，一个模块承担一个内聚职责。名称表达领域对象与动作，布尔值表达条件，避免难懂缩写、魔法数字、隐藏副作用和大段注释掉的旧实现。
- 使用清晰条件、提前返回和分层接口控制嵌套；同时保证所有退出路径释放已获取资源。C 的统一清理标签与 C++ 的 RAII 按目标环境使用，不能为了形式上禁止跳转而复制清理代码。

## 函数与文件长度

每个函数、方法、构造函数、析构函数和 lambda 的 **执行代码不得超过 50 行**。按格式化后的函数体统计含代码的物理行：计入声明与初始化、条件与循环、调用、返回、错误清理、宏调用及预处理分支中的代码；不计签名、空行、纯注释行和只有花括号的行。多行表达式占用的每个代码行都计入，内嵌 lambda 同时接受独立检查，不能借它隐藏超长主体。

- 不把多条语句挤到一行，不用宏或无意义的转发函数规避限制；格式器允许短单行函数，不意味着允许压缩复杂逻辑。
- 超过限制时，按独立职责、状态阶段或资源边界提取有意义的私有方法或辅助函数。把所需状态作为明确参数或对象成员传递，不以新增全局变量换取短函数。
- 代码文件非必要不超过 **2000 个物理行**，包含注释和空行。按内聚模块拆分实现与接口，同步构建、包含关系及文档分组；不为凑行数任意切片或删掉必要注释。
- 确有必要保留超长文件时，记录文件、实际行数、不可合理拆分的具体原因及维护方式。生成文件与第三方代码注明来源和生成入口，不手改生成物，也不以例外豁免普通业务代码。50 行规则不自行放宽。

使用项目已有语法感知工具辅助定位，再核对真实函数边界及上述口径。普通行数、正则和语句数量不等于函数执行代码行数；没有可靠工具时对本次受影响函数逐一审查并记录结果，不能假称全仓自动验证。

## 面向对象与高复用

- 先识别对象的状态、行为、生命周期与不变量，再决定接口。对象拥有自己的状态，通过公开操作维护有效状态；不把零散全局变量和过程函数改名后就称为面向对象。
- C 使用结构体实例、明确的实例参数和模块接口组织对象，按需要隐藏实现；确有多实现或可替换后端时再引入操作表与函数指针。C++ 用类封装不变量、用 RAII 表达资源所有权，优先组合，继承仅服务于真实替换关系。内核或 Zephyr 的 C 代码不为使用类而迁成 C++。
- 写新代码前搜索既有库、公共模块和调用方。将稳定、语义一致的重复逻辑收拢到唯一实现，平台差异放在清晰适配边界；不复制改名形成多套实现。
- 高复用以真实需求为依据。不因几行外观相似就合并不同契约，不为尚不存在的调用方造万能基类、插件系统或通用框架；避免仅含静态函数的无状态工具类。
- 明确借用与拥有、初始化与销毁、线程与中断上下文、锁与共享状态、成功与失败后的对象状态。依赖可测试且方向清晰；不要让复用层反向依赖具体业务。

## Doxygen 注释与手册

自有代码的文件、接口、类型、字段、枚举和非平凡内部函数使用 Doxygen 文档注释，说明默认用中文，标识符保持真实名称。记录目的、参数方向与取值约束、单位、空指针约定、返回与错误、所有权及生命周期；并发、阻塞、中断限制和失败副作用按实际契约说明。函数内部的必要注释解释原因与不变量，不逐行翻译语法。

接口声明处维护唯一契约，定义处补充实现原因；不复制两份会漂移的参数文档。模块分组、页面、示例与链接让输出能作为手册阅读，不只是函数名列表。按 [格式与手册生成](references/format_and_manual.md) 使用 Doxygen 模板并验证输出。Linux kernel-doc 与 Doxygen 不同，不能混写后声称两条生成链都已验证。

## 交付验证

1. 审查本次命名、函数执行行数、文件总行数、职责拆分、真实复用点与对象生命周期；说明必要的文件长度例外。
2. 用选定的配置及已确认版本执行格式检查，检查格式化差异，再运行与改动相符的编译、静态检查和测试；涉及资源或状态变化时覆盖失败、回滚与边界路径。
3. 实际生成文档，检查诊断与生成页面中的模块入口、类型成员、参数、返回值和交叉链接。工具缺失时如实写明“手册构建未验证”，不能仅凭注释格式宣称已生成。
4. 检查暂存差异，只交付本次范围。复用目标项目的提交、同步和发布流程；技能调用本身不授予提交、推送或发布权限。

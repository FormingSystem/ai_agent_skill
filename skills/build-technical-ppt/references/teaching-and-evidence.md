# 讲解、依据与可执行示例

> **语言 / Language** · **简体中文（当前）** · [English →](teaching-and-evidence_en.md)

## 先建立认识，再展开细节

选一个实际存在的官方应用或最小完整实例贯穿。说明读者当前有什么、缺什么、接下来解决什么问题，再引入工具或接口。称呼读者为“读者”，不用“学生、学员、同学”，不预设师生关系。

清楚区分下载、解压/安装、工程发现、配置、编译、运行和硬件验证。前置主机工具安排在使用之前；环境准备章不混入完整编译实验。读者需要从编译机制理解依赖版本时，解释其决定关系，把真正编译放回对应实验章。

每页围绕一个关系或操作组织，前页提出的问题由后页接续。正文说明完整因果，PPT 保留理解所需的关键环节，不用极短标签使读者只能听口头补充。备注适合放补充依据、讲述线索和历史批注，不承担唯一的执行前提。

通用接口体系独立成章，各模块回顾相关接口后再解释自身输入和产物。按认识变化拆主题；不设统一页数上限，也不为了显得精简删掉读者需要的分支。

用户指定篇幅时，以该限制为准。先列本册必须回答的少量核心问题，给每页一个明确作用，再检查是否重复。下载与接入类主题先用包关系图和安装后的目录解释对象，再按“获取 → 安装 → 交给使用方 → 验证实际选择”组织操作。技术依据靠近结论，避免为了展示源码而把读者带入整套构建体系。

融合参考稿时保留其有用的因果关系，校正技术错误、占位命令和不适用的建议；删除“整改目标”“建议替换大纲”等制作过程内容。PPT 保留一条能跟随的主线与必要替代入口，MD 承担下载异常、完整分支和深入依据。用同一概念重复做目录页、结论页、表格页，并不等于讲得更清楚。

可选配置必须在出现操作的位置标为可选，并与默认路线并列说明。不能先写成下一步必做，再隔多页补一句“其实不需要”。一个接口的完整示例须呈现传给谁以及成功看哪里；不只说“追加这个 -D”，也不把依赖未准备好的编译命令混进下载必做步骤。

## 工程机制必须有使用入口

教材承担解释成本。作者先读源码，提取“对象是什么、为何存在、谁读取、什么条件生效、读者做什么、结果如何判断”，再写成连续讲解；引用放在相应解释之后供核对。不能用“依据：链接；本地阅读某文件”结束一个尚未解释的机制，也不能把列出的源码路径当成内容本身。读者查源码应是在复核已理解的规则，而不是补齐作者省略的讲解。

比较官方路线与自行组装路线时，保持同一应用、硬件目标和可观察结果，逐项说明输入改变带来的责任变化。每个核心组件先核实它实际由主仓提供、外部清单取得还是工程自行接入；下载、被发现和真正进入编译是不同阶段。不得从某个厂商的包命名推导所有目标都需要同名包，也不得用“与另一个厂商无关”回避当前目标的实现究竟在哪里。

以包或模块接入为例，解释链应完整走过：

1. 使用方持有什么：应用目录、模块根、SDK 根、目标身份等。
2. 通过什么输入交给什么程序：参数、配置文件、环境、注册信息或项目清单。
3. 谁读取和发现：文件/函数、扫描范围、条件和默认行为。
4. 产生什么：解析后的目录、派生变量、生成记录、构建目标或命令。
5. 如何参与当前工程及验证：被执行的入口、加入的源码、头文件、编译器与产物。

之后再解释模块内部组织。把“如何给工程输入模块”与“模块的内部接入代码怎样组织”分开，避免一个问题只答了后半段。

说明接口时按需要覆盖：所属工具、用途、输入或派生结果、读取者、默认值或发现规则、值的形态、保存位置、有效范围、组合关系、取消和更新方法。不要机械为每个词建立大表。

特别区分当前终端环境、构建缓存、工程预设、当前用户注册信息和 Python 虚拟环境。说清“注册给哪个查找机制、由谁使用、能持续多久”，不用笼统的“永久配置”。先示范默认发现成功的普通路线，再解释固定版本或主动换类型等条件路线，不能把可选接口写成必做操作。

## 文件与来源

首次要求读者打开或修改文件时，标明以下状态之一，并就地说明位置和产生动作：

| 来源/状态 | 应解释的内容 |
| --- | --- |
| 官方源码原有 | 相对哪个源码根，核对哪个版本，阅读还是修改 |
| 官方外部下载 | 下载工具/清单/发行附件，落盘位置与版本依据 |
| 教程随附 | 材料入口、如何取用，不暗示官方树里原本存在 |
| 读者自行创建 | 创建文件还是目录、完整位置、内容与创建阶段 |
| 工具生成 | 哪条操作产生、成功后何时应出现，缺失时返回哪一步 |

目录不存在不立即判成误删，先确认阶段、根目录、版本和来源。只读摘录在正文、代码块及 PPT 就地标明，不让读者把摘录当成必须新建或替换的文件。

优先使用上游支持的工具和清单获取受管理依赖，核对 revision 与实际目录。网页用来查来源、发行资产、维护状态或解释选择；手动 ZIP 用于确有必要的离线/工具不可用分支，不人为增加下载后改名或自建来源记录的必做实验。

网页路线写清站点、组织/仓库、页面或标签及搜索框的位置，并给直接链接。源码结论同时提供官方文档网页、仓库文档文件和读取代码的定位，行号只作辅助。固定提交与 latest 页面区别说明；升级后按当前源码核对。区分建仓、维护权限、清单收录、构建发现、芯片支持和实板可用，不能相互替代。

## 可复制操作

代码块/区明确是终端命令、配置文件内容、只读源码、接口形态示意还是预期输出。不要混排终端提示符和输出，让读者误复制。用对应语言高亮，注释必须符合该语言。

完整操作单元标出系统、终端、位置和前提。命令之后紧接含义、成功输出及失败检查；不要让读者在长代码与远处解释之间配对。终端切换时重新交代工作目录、路径写法和环境，不暗示变量跨 shell 自动继承。

优先使用项目原生变量。确需自定义变量时，说明其作者约定性质、定义位置和用途，每次复用在附近提示来源。避免把作者的路径测试、临时解释器或试验环境变成读者必做步骤。

一个代码区内保留完整换行、引号、缩进、续行符和注释。分步分页只能在操作边界拆；完整可执行脚本另给可打开的配套文件和正文锚点。配色靠同框内富文本，不靠拆成多个词语文本框。截图只作观察辅助。

## 编译与新增支持的示例

编译示例先确认当前源码里确实有该板，介绍芯片、架构、板目标名、所需依赖、应用、完整命令和可观察产物。官方教学中新建的虚拟板不能冒充当前树内现成支持。

新增开发板/芯片采用可对照的官方样式：参考板原文件与新增文件逐一对应，解释每个改动的理由及发现链，再逐步增加硬件身份、设备树、启动和驱动。读者应看懂修改如何让自己的目标进入构建，不能只下载已经完成的结果。

有“练习新增板”和“本次实际目标板”时明确两者分工，并都带入路线。QEMU 或官方参考板的成功不能写成目标板实测成功。

## 冷读验收

不借助作者脑中的隐含知识，从首个操作重新阅读：能否找到当前提到的文件；能否辨认命令还是配置；能否解释选择这个版本的依据；能否把输入连接到读取程序与输出；失败后能否判断是未下载、未发现、未加入构建还是运行异常。

若读者仍必须自行全仓搜索、猜文件来源或拼接截图命令，修复正文。补一张变量表、贴一堆官方链接或声称“视频会讲”不能替代这个修复。

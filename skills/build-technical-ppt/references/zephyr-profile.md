## SDK 与构建接口的区分

讲清三条路线并核对当前归档：完整 GNU SDK、Minimal SDK 补装目标工具链、独立目标工具链组件。前两条共用 SDK 自带 CMake 接口；独立 `toolchain_gnu` 组件不等于 Minimal SDK，没有 SDK 的 cmake 文件不意味着读者要手建。

解释目标架构、主机平台、发行版本与 GNU/LLVM 分别是什么维度；完整包的多个架构不是同一个编译器的多个版本。以当前版本 setup 帮助和源码确认 `/t`、`/c` 等动作，区分工具链安装与当前用户 CMake 包位置注册，不能只说“配置/登记”。

Minimal 自带 SDK CMake 接入文件，仅缺目标工具链；独立工具链归档才缺完整 SDK 框架。两种 SDK 包使用同一发现机制。组装同发行组件后既可自动发现，也可显式指定 SDK 根，不能将 `/c` 写成组装的必需收尾。明确区别主机 cmake.exe、SDK 的 .cmake 文件、Zephyr 源码的查找脚本；区别找到 SDK 包与目标 GCC 可用。`-D` 写入构建缓存，不能叫作只对一条命令有效。

以真实官方应用说明已注册 SDK 的默认发现，再解释固定 SDK 根、主动改变工具链类型及独立组件的条件路线。不要把 `ZEPHYR_TOOLCHAIN_VARIANT=zephyr` 写成每次必做。区分 `ZEPHYR_SDK_INSTALL_DIR`、`CROSS_COMPILE` 和 `TOOLCHAIN_ROOT` 的读取者及值形态；区分 BOARD/SoC、CPU/FPU 参数、架构与编译器前缀。

## CMSIS、HAL 与新增支持

入门讲解先从具体硬件和应用建立认识：MPS2 是什么板、AN386 与 Cortex-M4 的关系，展开官方板文档及应用示例的原意。先由 CPU/架构解释 CMSIS Core 接口需求，再由当前 Zephyr 接入代码与 manifest 确定配套 CMSIS 项目和修订并下载；CPU 型号本身不能独自决定 CMSIS 主版本或提交。之后用 MPS2 展开完整驱动模型及主仓/外部代码的分工，读者理解接口、实现、实例和选源以后，再沿相同结构讲 HC32F4A0 为什么选择外置 DDL 及怎样接入。普通自定义组件实验放在两条真实路线之后，不得取代它们。

讲清架构、芯片/SoC、板目标与应用的关系，也讲清实际构建入口：通常由 BOARD 选择板/限定目标并带出 SoC 与架构，由应用目录的 CMakeLists.txt 和 prj.conf 选择应用源码与配置；不能让读者误以为四者都是可随意组合的独立开关。用同一应用换板、同一板换应用作对照，解释 west 的板/应用/输出参数与 CMake 的 -DBOARD/-S/-B 如何对应。官方文档实际示例选了哪个目标与教程改选目标分别说明，不能把教程变体冒充原文。

变量在解决具体接入问题时引入：先给出源码目录及缺口，再演示输入位置、读取者、默认发现或显式列表、模块入口、派生变量及生成记录。对比式说明主仓模块适配目录与外部模块源码目录，并在 CMSIS 与 HAL 两条实际链上走到 CMake/Kconfig 选源；不能先列参数表再要求读者自行拼出原理。

先解释当前板目标自己的硬件支持从哪里来，并把以下边界讲清楚：通用设备 API 是上层契约；外设 IP 驱动实现某类寄存器接口；SoC 差异包括时钟、复位及硬件特例；板级设备实例提供地址、中断、引脚、连接和启用配置；HAL/DDL 可承担外设底层操作；源码模块负责源码的归属与构建接入。这些对象不能都笼统称为“驱动包”。树内/树外是源码维护位置，与通用/专用的复用范围、API/寄存器的代码分层是不同维度；独立仓库不自动带来解耦，树内代码也不等于全为板子私有。

以 MPS2/AN386 为对照时，从当前源码追踪一个完整外设实例：DTS 节点与 binding 定义硬件属性，compatible 对应驱动，再把设备树属性怎样进入 config、init、标准 API 操作表及设备实例讲明，最后追到寄存器操作。分开画两条链：构建时发现模块、Kconfig/CMake 选源、生成静态设备实例；运行时上层 API 经设备操作表进入具体函数。binding 不是驱动算法，compatible 的关联不是 Linux 式运行时 probe，不能以“由 Kconfig 管理”跳过实例配置和运行分派。

用同一实例解释所在目录的 Kconfig、CMake 和宏来源，不把“文件放进目录”说成自动生效。追踪 Kconfig 入口如何经 source/rsource 等语句读取子文件，符号在哪里声明、哪些依赖/默认值或输入决定最终值，以及结果怎样成为 CONFIG_ 宏与构建输入。区分 DTS 生成的 DT_ 宏、源码局部 #define、构建命令的 -D 宏；展示头文件或生成文件怎样进入当前翻译单元。分别说明 CMake 决定编译哪些源文件、C 预处理决定保留哪些代码、设备树实例宏展开哪些设备定义；为当前实例列出实际条件的来源、读取者和效果，不以宏清单替代选源过程，也不将某个版本的具体宏固化成普遍规则。

不能省略 xxx_defconfig。用当前板的实际文件说明 BOARD 如何确定板默认配置输入、xxx_defconfig 如何给出 CONFIG_ 赋值、应用 prj.conf 如何提出功能需求，以及合并和依赖求值后为何仍须检查最终 .config。区分 Kconfig.defconfig：它使用 Kconfig 语法为已有符号提供有条件的默认值，不是另一个 CONFIG_ 赋值片段，也不等于生成结果。用一个开关追到 .config、CMake 变量与 autoconf.h 的不同表示，说明显式输入仍受依赖约束；文件发现路径、合并顺序和限定目标命名按当前 Zephyr 版本核对。

解释 CMSDK UART 以外设 IP 命名而非以 MPS2 芯片/板名命名的理由，用当前存在的另一平台实例对照共享寄存器接口与各自地址、中断等配置。设备树移出可描述的硬件配置，不替代寄存器语义、初始化顺序或硬件缺陷处理。检查共享驱动是否含 SoC 特例；有耦合就如实说明，不把“可复用”说成“完全没有平台差异”。MPS2 路线须明确独立厂商外设 HAL/DDL 是否实际被消费、寄存器定义及操作在哪里，以及外部 CMSIS Core 与这些外设实现的分工；不能把标准设备模型当作已经拆出裸机库的证明。

引入 hal_xhsc 之前，先用同一层次对照 HC32：本工程选择复用已有 DDL 的寄存器定义和底层操作，Zephyr 适配层负责设备模型及系统接口；若直接写寄存器驱动，则这些实现、验证和维护责任由工程承担。根据当前实际代码说明选择理由与仍需自行适配的范围，不预设 HAL 必须存在、下载后自动获得板驱动或所有 HAL 源文件都应编译。HAL 是抽象层概念，DDL 是一些厂商使用的命名；模块化源码通常静态编入固件，不能称为 Linux 的 .ko。不能只写“不需要华大 HAL”来代替 MPS2 自身实现的解释。

同时核对厂商实际发布的 BSP、Pack 或驱动库。厂商有支持包与当前 Zephyr 路线依赖该包是两个事实，不能互相推导；串口等单个驱动只能作为追踪实例，整体仍须说明启动、中断、内存/时钟和所需外设的实现分工，以及板支持范围与当前应用启用范围的区别。

教读者从已知产品芯片型号判断依赖，而不是预先告知一个待下载包名。把实际查询及结果解释写进教材，沿“产品型号 → 当前 SoC/CPU 与所需功能的 Kconfig → 实际消费 CMSIS/HAL 的 CMake、头文件引用和实现 → 模块标识 → manifest 中的 URL/revision/path”追到底。每一跳说明为什么能关联到下一项；核对 module.yml 的模块名、west 项目名与落盘目录的实际映射，不能默认三个名字相同。BOARD 用于定位支持链，CPU 用于解释 Core 接口需求，二者都不能单独推出 CMSIS 版本；实际使用哪一代接入、哪一项依赖必须由当前消费代码证实，再由清单固定仓库与修订。

分开讲两个分支。已有支持时，从板文档和 SoC 身份找到现有配置、驱动与构建消费者，核对它们引用的外部模块，然后使用解析后的 manifest 下载配套修订；若板未列出但 SoC 已支持，说明应补板级描述而非直接认定芯片完全不支持。缺少 SoC/驱动移植时，先根据产品资料确认 CPU、外设与现有支持缺口，再选择可复用的架构、IP 驱动或厂商包并编写接入；教材必须标明哪部分是已有规则、哪部分是本工程新增选择，不能伪造一条上游已有的依赖链。厂商源码还须核对版本、许可与适配范围，下载本身不产生板支持。

清单不是某块板的自动依赖求解结果。模块存在标记和模块路径变量只表示发现/接入状态，不等于该目标需要它，也不是负责下载的功能开关；需求由实际消费者及其条件证明，下载由 west 项目或明确的外部获取动作完成。主仓缺少、清单未收录、源码已下载、模块已发现、功能已编译分别判断，再用最终配置、模块记录、编译命令及头文件路径确认实际使用。

受当前清单管理的 CMSIS 项目按上述消费链确定后，使用 west 获取并核对；网页用于确认来源，不能以手动 ZIP 改名取代工具主线。区分 Arm 通用 Core、芯片设备头、厂商 system/startup、HAL/DDL 和 Zephyr 接入层，同名头文件不能直接替换。

厂商模块地址给出完整查找路线：GitHub 的 Zephyr 组织仓库列表、具体搜索对象、仓库 README 和对应申请/PR。是否建仓、是否收录清单、是否被当前构建发现、是否有 SoC/板支持分别查证；Closed 不等于 Merged，状态注明核对时间。

从调用方说明模块列表输入、Zephyr 的发现脚本、`module.yml` 解析、生成记录和目录变量，再讲实际 CMake/Kconfig 接入。不能从模块自行“管理”跳到 `ZEPHYR_HAL_XHSC_MODULE_DIR` 自动存在。CMSIS 外置接入标志与实际 Zephyr 内置接入文件按当前源码解释。

编译教学要有当前源码真正支持的板与应用；新增教学要有官方样式的练习板对照，并带入真实 UYUP/HC32F4A0 目标。厂商、开发板与 CPU 架构层次分清，目录、YAML、Kconfig、SoC 和设备树按所用 Zephyr 硬件模型解释。芯片型号、晶振和 PDF 依据保留，HC32F460 资料不能冒充 HC32F4A0 依据。

## The difference between SDK and build interface

Explain the three routes and check the current archive: full GNU SDK, Minimal SDK patch target tool chain, and independent target tool chain components. The first two shared SDKs come with their own CMake interface; the independent `toolchain_gnu` component is not equal to Minimal SDK. The cmake file without SDK does not mean that readers have to build it manually.

Explain what dimensions target architecture, host platform, distribution, and GNU/LLVM are; multiple architectures of a complete package are not multiple versions of the same compiler. Use the current version setup help and source code to confirm `/t`, `/c` and other actions. Distinguish between tool chain installation and current user CMake package location registration. Do not just say "Configure/Register".

Minimal comes with its own SDK CMake access file and only lacks the target tool chain; the independent tool chain archive lacks the complete SDK framework. Both SDK packages use the same discovery mechanism. After assembling the components of the same release, it can be automatically discovered or the SDK root can be specified explicitly. `/c` cannot be written as a required end of the assembly. Clearly distinguish the host cmake.exe, SDK .cmake file, and Zephyr source code search script; distinguish the found SDK package and the target GCC available. `-D` is written to the build cache and cannot be said to be valid for only one command.

A real official application explains the default discovery of the registered SDK, and then explains the conditional route of fixing the SDK root, actively changing the tool chain type and independent components. Don't write `ZEPHYR_TOOLCHAIN_VARIANT=zephyr` as a must-do every time. Distinguish the readers and value forms of `ZEPHYR_SDK_INSTALL_DIR`, `CROSS_COMPILE` and `TOOLCHAIN_ROOT`; distinguish BOARD/SoC, CPU/FPU parameters, architecture and compiler prefixes.

## CMSIS, HAL and new support

The introductory explanation first establishes an understanding of the specific hardware and applications: what kind of board MPS2 is, the relationship between AN386 and Cortex-M4, and unfolds the original meaning of the official board documents and application examples. The CMSIS Core interface requirements are first explained by the CPU/architecture, and then the supporting CMSIS projects and revisions are determined and downloaded by the current Zephyr access code and manifest; the CPU model itself cannot independently determine the CMSIS main version or submission. After that, MPS2 is used to expand the complete driver model and the division of labor between the main repository/external code. After the reader understands the interface, implementation, examples and source selection, we will then follow the same structure to explain why HC32F4A0 chooses external DDL and how to access it. Normal custom component experiments are placed after the two real routes and must not replace them.

Explain clearly the relationship between architecture, chip/SoC, board target and application, and also explain the actual construction entrance: usually BOARD selects the board/limited target and brings out the SoC and architecture, and CMakeLists.txt and prj.conf in the application directory selects the application source code and configuration; readers must not be misled into thinking that the four are independent switches that can be combined at will. Use the same application to change the board and the same board to change the application as a comparison to explain how west's board/application/output parameters correspond to CMake's -DBOARD/-S/-B. The official document explains which target is selected in the actual example and the target selected in the tutorial respectively. Tutorial variations cannot be passed off as the original text.

Variables are introduced when solving specific access problems: first give the source code directory and gaps, and then demonstrate the input location, reader, default discovery or explicit list, module entry, derived variables and generated records. Comparatively illustrate the main repository module adaptation directory and the external module source code directory, and go to the CMake/Kconfig source selection on the two actual chains of CMSIS and HAL; you cannot first list the parameter list and then ask the reader to spell out the principle on their own.

First explain where the current board target's own hardware support comes from, and make the following boundaries clear: the general device API is the upper-layer contract; the peripheral IP driver implements a certain type of register interface; SoC differences include clock, reset and hardware special cases; the board-level device instance provides address, interrupt, pin, connection and enable configuration; HAL/DDL can undertake the underlying operations of the peripheral; the source code module is responsible for the ownership and construction access of the source code. These objects cannot all be collectively called "driver packages". In-tree/out-of-tree are source code maintenance locations, which are different dimensions from general/dedicated reuse scope and API/register code layering; independent repositories do not automatically bring about decoupling, and the code in the tree does not mean that all the code is private to the board.

Using MPS2/AN386 as a comparison, trace a complete peripheral instance from the current source code: DTS nodes and binding define hardware attributes, compatible corresponds to the driver, then explain how the device tree attributes enter config, init, standard API operation tables and device instances, and finally trace the register operations. Two chains are drawn separately: module discovery during build, source selection by Kconfig/CMake, and static device instance generation; the upper-level API at runtime enters specific functions through the device operation table. The binding is not a driver algorithm, the compatible association is not a Linux-style runtime probe, and instance configuration and run dispatch cannot be skipped as "managed by Kconfig".

Use the same example to explain the source of Kconfig, CMake and macros in the directory, and do not say "put the file into the directory" as automatically taking effect. Trace how the Kconfig entry reads subfiles via source/rsource statements, where symbols are declared, which dependencies/defaults or inputs determine the final value, and how the results become CONFIG_ macros and build inputs. Distinguish between DT_ macros generated by DTS, source code local #defines, and -D macros of build commands; show how header files or generated files enter the current translation unit. Explain respectively which source files CMake decides to compile, which code C preprocessing decides to retain, and which device definitions the device tree instance macro expands; lists the sources, readers, and effects of actual conditions for the current instance, and does not replace the source selection process with a macro list, nor solidify a certain version of specific macros into universal rules.

xxx_defconfig cannot be omitted. Using actual files from the current board, explain how BOARD determines the board default configuration input, how xxx_defconfig gives CONFIG_ assignments, how applying prj.conf makes feature requirements, and why the final .config must still be checked after merging and dependency evaluation. Distinguish Kconfig.defconfig: it uses Kconfig syntax to provide conditional default values ​​for existing symbols, is not another CONFIG_ assignment fragment, and is not equivalent to the generated result. Use a switch to trace the different representations of .config, CMake variables and autoconf.h, indicating that explicit input is still subject to dependencies; file discovery paths, merge orders and qualified target naming are checked according to the current Zephyr version.

Explain the reason why the CMSDK UART is named after the peripheral IP instead of the MPS2 chip/board name, and use another currently existing platform instance to compare the shared register interface and its respective address, interrupt and other configurations. The device tree moves out of the describable hardware configuration and does not replace register semantics, initialization order, or hardware defect handling. Check whether the shared driver contains SoC special cases; if there is coupling, explain it truthfully, and do not say "reusable" as "no platform difference at all". The MPS2 route must clarify whether the independent vendor peripheral HAL/DDL is actually consumed, where the registers are defined and operated, and the division of labor between the external CMSIS Core and the implementation of these peripherals; the standard device model cannot be regarded as proof that the bare metal library has been removed.

Before introducing hal_xhsc, first use the same level to compare HC32: This project chooses to reuse the register definitions and underlying operations of the existing DDL. The Zephyr adaptation layer is responsible for the device model and system interface; if the register driver is written directly, these implementation, verification and maintenance responsibilities will be borne by the project. According to the current actual code description selection reasons and the scope that still needs to be adapted by itself, it is not preset that HAL must exist, the board driver will be automatically obtained after downloading, or all HAL source files should be compiled. HAL is an abstraction layer concept, and DDL is a naming used by some manufacturers; modular source code is usually statically compiled into firmware and cannot be called Linux's .ko. You cannot just write "BGI HAL is not required" instead of explaining the implementation of MPS2 itself.

Also check the BSP, Pack or driver library actually released by the manufacturer. The fact that the manufacturer has a support package and the current Zephyr route relies on this package are two facts that cannot be deduced from each other; a single driver such as the serial port can only be used as a tracking instance, and the overall implementation division of startup, interrupt, memory/clock, and required peripherals must still be explained, as well as the difference between the board support range and the current application enablement range.

Teach readers to determine dependencies from known product chip models, rather than telling them a package name to be downloaded in advance. Each hop explains why it can be related to the next item; check the actual mapping of the module name, west project name and download directory in module.yml, and the three names cannot be the same by default.

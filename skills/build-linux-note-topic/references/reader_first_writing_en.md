# Text entry, terminology and continuous reading access control

> **Language / 语言** · [← 简体中文](reader_first_writing.md) · **English (current)**

This document must be read in its entirety before designing, reorganizing, creating, expanding, or rewriting a topic, and reviewed against it before delivering it chapter by chapter. Only the typesetting task still obeys the authorization boundary of the main entrance, and technical content is not rewritten by discovering teaching gaps.

## Let modules, platforms and generations be built from scratch

Work-type blueprints can use author classifications such as "universal model + implementation on multiple platforms + intergenerational comparison", but these labels only help the author break down the material and **should not directly become a reader's entry point or imply prerequisite knowledge**. Ground zero means not only explaining abbreviations, but also that the reader initially has no idea why these modules exist, what a platform is, which names are on the same layer, and on what axis of change the versions or generations are divided.

Before each module, classification axis, platform, architecture, product, implementation family, version or generation assumes the responsibility of reading triage or comparison for the first time, it must first complete the following closed loop:

1. **What it is:** Use aligned common language to describe object types and plain meanings, without using the same set of unfamiliar names to define each other;
2. **Why it comes about:** Deriving it from a specific problem, constraint, or gap in an old model rather than declaring a mature classification first;
3. **Who it is connected to:** Specify the upstream input, downstream output, hierarchy, owner and position in a minimum transaction;
4. **What is it different from:** First give the comparison axis, and then distinguish adjacent concepts. Different levels such as manufacturer, architecture, processor core, chip, development board, standard version and driver cannot be directly juxtaposed;
5. **What the reader can do now:** Close a minimal process or identity positioning of this object before it enters a classification table, variant matrix, platform longitudinal implementation, or generational comparison.

In particular, the coordinate relationship must be established first for hardware and platform topics, such as "standard or instruction set architecture → processor core or controller implementation → SoC integration → development board connection → firmware and operating system driver". The specific topic tailors this chain based on facts, but it must answer who defines each name, which layer it belongs to, and how it combines with adjacent layers. The first platform first completes its own identity and complete affairs, and subsequent platforms or new generations are naturally introduced by new scales, new capabilities, or new constraints; only after the objects on both sides have been independently established, the commonalities and differences are summarized.

Therefore, when the author gets the combined goal, he must convert it into a reader causal chain: **Realistic events or tasks → Naive model → Current gap → New module and name → Identity and relationship coordinates → Minimum closed loop → Specific implementation → Variants or generations driven by new constraints → Comparison between established objects**. Do not pass off the final structure of the topic that the author already knows as the knowledge structure that the reader already has.

## First determine the classification axis and module variant matrix

When a topic has both **public concepts/API** and**multiple implementation families, configuration branches, or execution models**, the topic-level classification must be completed before the text is generated. The names on different axes cannot be mixed into a string of "types", nor can one directly select a variant to talk about the complete system vertically.

1. First derive public responsibilities and possible changing dimensions from specific problems, and then name orthogonal axes such as public contracts, protection domains or semantic flavors, implementation families, execution models, operating strategies/optimizations, and diagnostic facilities; the same name can only participate in comparisons on the axis to which it belongs.
2. Classification coordinates must enter later than the concepts that make up the coordinates and before the first variant is internally implemented. Before readers enter branches such as "preemptive/non-preemptible", "polling/interrupt", "synchronous/asynchronous", etc., they should already know what each word is, why they form this comparison axis, which semantics and modules coexist, and what this branch only changes.
3. First establish public concepts, common interfaces and a round of public end-to-end skeleton, and then establish a **Module × Variant Matrix**: rows are functional modules that can be learned independently, and columns are public responsibilities, public implementation, differences of each variant, source code/standard evidence and corresponding experiments.
4. The default is to advance by module: each module first talks about concepts, input and output, and public responsibilities, and then compares how the variants change participants, status, communication, completion conditions, and costs. Common GPs, queues, topologies, lifecycles, or error handling may not be duplicated in multiple variant chapters.
5. Only if a variant does change most of the end-to-end participant set, proof method, control flow and completion conditions, then a complete vertical chapter is allowed to be established for it; if the difference only falls in one or a few modules, a side-by-side comparison will be made within the corresponding module.
6. Composite application, object life cycle, diagnosis and selection cannot be inserted into the necessary pre-chain of "public interface → classification coordinate → public skeleton"; they enter their respective stages after the basic mechanism is established.
7. An experiment can either be orchestrated centrally or must be linked back to the specific concept or variant difference it demonstrates. Do not write only abstract conclusions in the text and end up with a catalog of experiments that cannot correspond to the previous proof obligations.

The book blueprint must be able to answer: What content remains the same across variants, what belongs only to a certain variant, and why "compare by module" or "slice by variant". If the two variant chapters repeatedly talk about the same group of public executors, state carriers and complete cycles, it means that the main theme of the topic is likely to be reversed and must be redesigned before writing the main text.

## Establish a fixed reader entrance for explanatory chapters

When creating or supplementing explanatory chapters such as concepts, syntax, interfaces, configurations, and source code introductions, do not list definitions, fields, APIs, or classification tables directly after the title. First establish the background in the following order; these six steps are a content contract and do not require mechanical writing of six titles with the same name:

1. **Recycle pre-conclusion:** Explain what effective understanding the reader has gained from the previous chapter, upper-level mechanism or common practice, to avoid writing existing knowledge as errors.
2. **Fixed actual encounters:** Select a well-structured piece of code, configuration, log, call path, or operation site to explain where readers usually encounter the topic of this chapter and what tasks they were completing at that time.
3. **Exposing remaining gaps:** List specific questions that cannot be answered by current models alone, and explain why guessing by name, superficial syntax, or condensed conclusions leads to incorrect judgments.
4. **Locate the level of this chapter:** Explain which layer of definition, syntax, abstraction mechanism, implementation, runtime, diagnosis or engineering process the problem belongs to, and how it is connected to the previous and next layers.
5. **Limit the boundaries of the explanation:** Make it clear what this chapter only solves, which authoritative topics are not repeated, and which issues are intentionally left to the next chapter to prevent the background from evolving into an overview of mature terms.
6. **Declare testable results:** Conclude the background with actions that readers can perform after completion, such as being able to manually expand, draw a timeline, determine interface preconditions, locate status addresses, or select verification evidence; then the text continues to reuse the same scene and object.

Background is not a chapter summary, nor is it a "very important or complex" motivation. After completing the entry, the reader should be able to answer "Why do I need this chapter now, which scene should I take with me to read on, and what extra step can I take after reading it?" If the existing beginning has completely covered these three questions, there is no need to add a second background.

## Performing anti-formalism and hard-gated continuous reading

When creating, extending, or rewriting text, having all the elements in place does not mean that the chapters are qualified**. Just because the document already contains scenarios, glossary, S0~Sn, Mermaid, source code links, version boundaries, and checklists does not mean it is complete. The following mandatory acceptance gates are implemented chapter by chapter before delivery; any failure must continue to be modified and cannot be offset by "the link is valid", "the evidence has another authoritative location" or "the topic has been discussed in other chapters":

1. **Title Contract:** If the title promises any reader task among "concept", "problem", "mechanism", "source code implementation", "experiment" or "navigation", the text must be fulfilled locally. When the title contains promises such as "source code implementation, source code explanation, source code mechanism", each main implementation module must explain the implementation principle, input and output, key status and source code evidence in the current chapter; if the main text is only responsible for establishing a stable model or organizing links, an accurate title should be used instead, and readers must not click in to find out that they need to jump.
2. **Broken link reading:** Assuming that the reader prints this article, hides the URL, and does not click on any links, he should still be able to reconstruct the basic concepts, background problems, solutions, key state transitions, and conclusions of this chapter along the text. The link can only verify, deepen or enter the unique source code function body, and cannot bear the first explanation of a concept, module responsibility or key cause and effect.
3. **Module local closed loop:** When each major module appears for the first time, "basic concepts and type positioning → problems faced by the current module → solutions and status/communication → predictions or counterexamples left for readers → implementation verification or source code evidence". These five items are a closed loop of content and do not require the machine to use five titles with the same name; it is not allowed to dump all fields across modules first and then explain them in reverse later.
4. **Type Hierarchy:** Before mixing terms in the same paragraph, table or panorama, differentiate between abstract concepts, execution roles, state carriers, process stages, configuration variants, optimization branches and diagnostic mechanisms. Different types of objects such as GP, GP request, GP kthread, `rcu_state`, SRS and stall cannot be thrown directly to the reader as a set of side-by-side "concepts".
5. **Term dependencies are available:** Establish names, meanings, responsibilities, and necessary boundaries in place for new abbreviations, proper names, configurations, source code symbols, or internal stage names required for current reasoning; one string of unknown words cannot be used to explain another unknown word. The prerequisite knowledge that has been clearly established in the consecutive textbooks allows for a brief review, and the title or phenomenon to be explained does not assume the prerequisite for understanding; classification, comparison, and mechanism reasoning must be based on the understanding that the reader has already acquired.
6. **Mainline priority:** First select a default configuration and normal path to close the mainline; optimization, version differences, diagnostics, abnormal slow paths and other execution models can only appear as branches after the mainline is established. You must not interrupt the problem being solved in this chapter for the sake of complete coverage, nor must you tell the counterexamples in the next chapter that will create cognitive suspense in advance.
7. **Indicates increment:** A second mechanism sheet, mechanism diagram, or second set of stage numbers must answer new questions that the previous one cannot answer. Simply translating the same process repeatedly between timelines, bit charts, relationship diagrams, stage tables, function lists, and evidence tables is a form of stacking and must be merged or deleted. An exception is the reuse of the same image for reader orientation: keep the unified route and numbering, only highlight the current position, and do not pretend to explain the new mechanism.
8. **First screen and independent reading review acceptance:** Before the source code file list, version ledger and dense links, readers must first know "why they are reading now, which scene they are following, and what they can accomplish after reading." During the review, the main line is recited in five to eight sentences from the perspective of a reader who did not participate in the writing; if it is necessary to click on a link, search for the following text, or first understand the test editor before retelling, the chapter is not qualified.
9. **Title hierarchy is not decoration:** H2 cannot just retell H1 without "Chapter N", nor can it go directly to the next title without any connecting text. Empty headings, heading echoes, and umbrella subsections created only to satisfy the number of levels must be changed to real reading tasks, or deleted and renumbered.
10. **Cross-title continuity:** Read the last paragraph of the previous section, the title and the first paragraph of the next section, and check whether the objects, conditions, references and questions are continued. Then temporarily cover the title and check whether the reasoning premise has been lost or the scene has suddenly changed in the text; the classification and navigation information of the title do not need to be repeated verbatim, but the explanation of the conclusion, change conditions and key cause and effect must be established in the text. Only "Next" or repeated titles cannot be considered repairs, and the actual gaps must be filled; this is semantic independent reading review and cannot be replaced by keyword or paragraph length detection.

For detailed criteria, see [Continuous Reading and Anti-Formalist Acceptance](reader_continuity_review_en.md) and [references/review-checklist.md](review-checklist_en.md). The source code chapter must also implement the "Links can only serve as evidence and cannot replace explanations" of [references/source-evidence.md](source-evidence_en.md).

## Beginner terminology acceptance gate: align language first, then expand concepts

The default reader is **who has general computer knowledge, but has not yet mastered the private vocabulary of the current topic**; the programming, engineering or other basics that the user has already explained should be retained and no repeated make-up lessons will be allowed. Do not assume that the reader understands a term just because it appears in the kernel source code, official documentation, previous chapters, developer conversations, or topic titles. Completeness of explanation and continuity of thinking should be given priority over length; when there are too many terms, the learning stages should be divided according to knowledge dependence, and specific questions should be used to gradually introduce them. Compressed explanations should not be exchanged for short articles, and large glossaries should not be used instead of text progression.

Establish a working **term dependency ledger** before writing, recording at least: original writing, formal English full name or name nature, accurate Chinese name, term type, simple definition, current scenario responsibilities, pre-terminology, easily confused items, version/configuration boundaries, first appearance location and authoritative precise entry. Arrange the text in order of dependency; a definition can only use words that have been aligned. If an unfamiliar term appears in the explanation, explain it recursively. You cannot use a string of new slang to explain old slang.

The scope of inspection includes title, navigation, text, tables, figures, code, configuration and logs, but it is necessary to distinguish between "proposing a learning object" and "treating it as a known premise". Titles that ask questions, show short codes or error phenomena to be explained, and then explain them are allowed teaching sequences; requiring readers to understand unexplained concepts before continuing reasoning is a breakpoint that needs to be repaired. The continuous textbook completes necessary explanations when the concept is first established, and subsequent chapters maintain continuity with brief reviews and accurate front-end entries, without mechanically repeating the full English name and the entire set of definitions. A stand-alone introductory article completes its own premises within the scope of its commitment.

The first time a term takes on reasoning responsibilities, an "entry card" is completed by scope of application:

1. **Name and prominence:** For the first time, the overall bold definition is**Chinese Name (English Full Name, ABBR)**; concepts without popular abbreviations use**Chinese Name (English Full Name)**. If the command, product model, project, implementation family, historical nickname, and source code identifier are not abbreviations, indicate the nature of the name, and the full name must not be made up. Subsequent general mentions do not need to be repeatedly expanded or all bolded; the title, code and Mermaid maintain the original syntax, and the names are contrasted and highlighted immediately in the text.
2. **Type:** Indicate whether it is an abstract concept, public contract, execution role, state carrier, process stage, implementation family, execution model, strategy optimization, diagnostic facility, configuration item, source code macro/function/field, language syntax, file format, build artifact, or observation tool. Different types shall not be compared on the same level without explanation.
3. **Plain Meaning:** Answer "what exactly is it" in a sentence or two that doesn't rely on the jargon of this topic, and then introduce a precise definition. Analogy can only assist, not replace definitions and boundaries.
4. **Current Responsibilities:** Describe why it appears in this scenario, what it reads or receives, what it writes, outputs or changes, who owns it, and in which event or phase it takes effect.
5. **Boundary and Confusing Items:** Explain what it does not guarantee, who it is most likely to be confused with, and which classification axis the two are distinguished from; mark it immediately if version, architecture or Kconfig changes the meaning.
6. **Local explanation and in-depth entry:** First write the minimum explanation of the current chapter that is enough to continue reading, and then give the precise title anchor point in the text, the precise title of the authoritative topic or official information. Links are used for in-depth and evidence-gathering purposes and must not replace the first local explanation; a single sentence of a local explanation must not pretend to be a complete and authoritative explanation.

When multiple unfamiliar words need to be introduced in the same section, first check whether multiple learning stages are squeezed together. Prioritize exposing a knowledge gap from specific tasks, explaining necessary names, establishing concepts with observable processes, and then moving on to the next concept. The "entry card" is the explanatory responsibility that the author should complete. It does not require readers to memorize a set of definitions first, nor is it a fixed field template that must be repeatedly displayed in the text. Only when the comparison object has been established can the classification table, relationship diagram or mechanism deduction be entered. Private names in tables and figures must be accompanied by the necessary explanation; further reading references are linked to the **Full Title Anchor** and links cannot be used in place of explanations on which the current inference relies.

Topic project-specific naming must also explain the naming subject and scope: who defined the name, does it refer to a concept or a version of an object/state/implementation, where is the state saved and who owns it, and what is its relationship to the general concept. Seemingly ordinary English words such as tree, tiny, tasks, flavor, debt, and epoch, once they acquire special meanings within the topic, are treated as proper nouns, and readers cannot be relied on to guess the meaning.

Only after term dependencies have been cleared can type comparisons, causal deductions, source code chains, or configuration matrices begin. During delivery, names in titles, tables, figures and codes are randomly selected for independent reading review testing: readers should be able to tell the Chinese and English names or the nature of the name, its type, current responsibilities, boundaries and precise in-depth entry without searching for external information. Automatic auditing can only find candidate words and obvious first-occurrence risks, and cannot replace this manual judgment.
